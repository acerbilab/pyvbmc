# PyVBMC 1.5: the big picture

*Release outline agreed on 6 September 2026; refreshed on 10 September 2026.*

PyVBMC 1.5 makes the existing VBMC method faster, more dependable and easier
to use in a broader modelling workflow. The NumPy/SciPy modernization, the
main correctness repairs and the model and posterior integration work are
implemented. A bounded PyTorch feasibility study is also complete. Its
evidence supports retaining the modernized NumPy/SciPy solver for this release,
with no full Torch solver port.

## What users should gain

**Faster runs and lower memory use.** PyVBMC now does less work between calls
to the user's model. Candidate evaluation, posterior-density calculations,
entropy and Gaussian-process integral work have been vectorized; GP prediction
and hyperparameter-sampling overhead have been reduced with GPyReg; and
expensive GP factors and optional noisy-acquisition details no longer inflate
ordinary optimization histories. The practical benefit still depends on how
much of a run is spent inside PyVBMC rather than evaluating the target.

| Measured outcome | Before | After | Change |
| --- | ---: | ---: | ---: |
| Total runtime across 280 benchmark runs | 9.92 h | 4.71 h | 2.11× speedup; 53% less time |
| Retained history, noisy logistic D=5, seed 0 | 117.3 MB | 4.6 MB | 96% less |
| Peak process memory, same noisy logistic run | 427 MB | 273 MB | 36% less |

The runtime comparison covers the same 14 configurations and 20 seeds before
and after the main numerical modernization, on one laptop with one BLAS thread.
The memory comparison isolates the history repairs on the same trajectory.
Random streams and trajectories changed between the runtime campaigns, but
the population comparisons found no flagged differences. These measurements
precede the complete 1.5 release candidate; its final benchmark remains pending.
See the [benchmark plan](plans/benchmark-suite-and-golden-traces.md),
[modernization roadmap](plans/modernization-roadmap.md) and
[memory plan](plans/stage2-memory.md) for the full evidence.

**Optional performance tuning for your machine.** Users can run
`pyvbmc.calibrate()` to tune posterior-density and entropy calculations for
their computer. PyVBMC saves compatible settings for future runs and retains
standard settings when tuning offers no reliable improvement. Calibration
runs only when requested, shows progress, and never evaluates the user's
model; selected settings stay fixed throughout each inference run.

**More reproducible and dependable inference.** Each run has its own seeded
random-number stream, shared throughout PyVBMC and GP fitting without changing
NumPy's global state. Saves retain the information needed to resume that
stream. Explicit generator support addresses the core request in
[issue #138](https://github.com/acerbilab/pyvbmc/issues/138), which we plan to
respond to after the 1.5 release. Lower-precision inputs are widened consistently
to float64, and the parameter-transform, option and supporting-utility defects
selected for 1.5 have been repaired.

The numerical repairs improve how the solver learns from past GP fits,
balances acquisition scores and decides when to stop sampling GP
hyperparameters. An unnecessary penalty in variational optimization has
also been removed.
The final boost, which gives the fitted posterior one larger last refinement,
now omits its component-weight penalty and rejects a candidate when
either its estimated evidence or its uncertainty-adjusted score deteriorates
beyond the selected tolerance.
This protects against deterioration in the estimated scores, but does not
guarantee a more accurate posterior; its tradeoffs remain part of the final
population check.

**An easier route from a model to a fitted posterior.** Existing torch or JAX
models can be connected through a small adapter and an opt-in batch interface
for the initial design. The workflow supports ordinary and noisy targets,
supplied function values and separate scalar priors. Later active-sampling
calls remain sequential, because each selected point updates the GP before
the next one is chosen.

**An easier route from a fitted posterior to other tools.** `vp.to_torch()`
exports an independent distribution for sampling and differentiable density
evaluation, including bounded-parameter transformations and explicit dtype
and device choices. `vp.to_arviz()` exports named posterior draws using the
current ArviZ DataTree representation. Both integrations are optional; normal
NumPy/SciPy use requires neither torch nor ArviZ.

**A sound base for future methods.** The modernization gives future algorithm
work clearer numerical seams and stronger tests. Richer posterior families,
gradient-based acquisition optimization and larger-scale inference remain
separate research projects rather than promises of 1.5.

**Useful guidance during ordinary runs.** Occasional startup tips help users
choose starting points, check their results and discover related tools, with
links to further guidance. Tips do not repeat within a Python session and
give priority to calibration reminders. Set `show_tips=False` to disable
them; quiet mode suppresses both types of guidance.

S-VBMC combines posteriors from several completed VBMC runs. Compatibility
checks with the current PyVBMC code passed, including stacking and optimization
of real fitted posteriors. The planned integration would make this existing
method directly available through PyVBMC and establish a common delivery
approach for related methods.

A NumPy prototype reproduced S-VBMC's float64 calculations and showed useful
performance improvements, but most of those gains also transfer to Torch
through shared preparation optimizations. The
[integration proposal](2026-09-08-ecosystem-integration.md) recommends
retaining Torch and the existing S-VBMC object workflow, with optional
dependencies and a migration route for current users. These recommendations
await review from S-VBMC's main developer before integration proceeds.
See the [prototype results](results/2026-09-09-svbmc-numpy-prototype.md)
for the timings, controls and limits of this three-example CPU study.

## Why we can make these changes confidently

The modernization adds finite-difference checks for the hand-derived
gradients, fixed MATLAB comparisons, stage-level numerical oracles and replay
of complete optimization trajectories. The benchmark collection covers
varied posterior shapes, dimensions and noise levels. These checks distinguish
intended numerical changes from ordinary run-to-run variation and provide
accuracy fences for changed trajectories.

The extended 870-run reference across 19 configurations is complete and
validated. The final-boost policy was studied through paired comparisons
from those saved endpoints. These studies do not replace the final integrated
benchmark on the release candidate after all correctness changes, which
remains pending.

Variational stopping-rule research and the separate GPyReg step-out issue
are deferred work, not release blockers.

For the full numerical evidence and its limits, see the
[numerical-campaign summary](2026-09-08-numerical-campaigns.md).

## What the PyTorch feasibility study established

The feasibility study compared complete variational fits using NumPy on CPU
and Torch on CPU and GPU, including GP integrals, entropy, optimization and
posterior selection. It covered both ordinary fits and larger final refinements.

The prototype showed useful float64 agreement for objective values and
gradients on fixed inputs, with some differences in auxiliary state and
accumulated drift over complete fits. GP models were held fixed, so the study
does not establish the speed or reliability of a complete Torch solver.

Without compilation, Torch took 2.12–6.26 times the NumPy runtime on CPU and
3.35–23.34 times on GPU across eight workloads. These were individual timing
observations on one Windows laptop, using one CPU thread and an RTX 4060 Laptop
GPU, with GPU execution synchronized. Fit timings include preparation and
transfers; imports and device startup were measured separately.

The backend decision weighs numerical reliability, CPU and GPU performance,
startup costs, implementation simplicity and installation impact together.
Autodiff simplified parts of the gradient calculations, but preserving the
estimator still required substantial supporting machinery. The prototype did
not demonstrate an overall implementation simplification, and its installation
footprint and setup costs also favor retaining NumPy in 1.5.

A [compiled-Torch follow-up](results/2026-09-09-torch-compile-follow-up.md)
showed that compilation materially improves GPU performance on the larger fits.
The table gives warm median times in seconds across three matched seeds for
four workloads, including final scoring and synchronized GPU execution.

| Workload | NumPy CPU | Eager Torch CPU | Compiled CPU | Eager CUDA | Compiled CUDA |
| --- | ---: | ---: | ---: | ---: | ---: |
| Deterministic D2/K1 | 0.00434 | 0.0188 | 0.00867 | 0.0756 | 0.0236 |
| Warped D5 | 0.274 | 0.722 | 0.574 | 1.16 | 0.406 |
| Sampled-GP boost D4/K50 | 1.48 | 3.94 | 3.16 | 4.48 | 1.19 |
| Synthetic boost D15/N750/K50 | 7.90 | 24.7 | 30.4 | 34.1 | 5.13 |

On the two boost cases, compiled GPU fits achieve median paired warm speedups
over NumPy of about 1.28x and 1.54x.
Compiled CPU remains roughly 2-4x the NumPy runtime by the per-arm medians.
Cold compiled first fits take 23-444 seconds on CPU and 12-122 seconds on CUDA,
before separately reported setup.
These warm results assume reusable shapes and caches; they do not measure a
full run with a growing GP. A sampled-boost seed also shows endpoint parameter
drift despite small rescored ELBO differences. The evidence supports further
compiled GPU work, but does not establish a sufficient overall benefit for a
solver port in 1.5. PyVBMC therefore retains NumPy/SciPy, alongside the optional
Torch and ArviZ posterior exports.

The complete design, timing table, numerical gates and installation evidence
are in the [Stage 4 feasibility plan](plans/stage4-torch-feasibility.md).

## What remains before release

1. Integrate the existing S-VBMC implementation for 1.5. Compatibility is
   complete; review the proposed code placement, preserved public workflow,
   optional dependency and migration contracts before integration work starts.
2. Resolve the follow-up from the completed
   [273-run population assessment](results/2026-09-11-overnight-population.md).
   It recommends 30 additional runs for noisy Rosenbrock and logistic
   regression before deciding on reference promotion. Numerical assessment
   can proceed alongside skill and S-VBMC work that leaves ordinary inference
   unchanged.
3. Complete the final documentation, release records and publication work.

The planned user-facing `skills/pyvbmc/SKILL.md` remains part of the release
follow-up: guidance and small helpers for coding agents to set up, diagnose
and interpret PyVBMC runs, kept consistent with the final public API. See the
[user-agent skill proposal](2026-09-02-user-agent-skill.md).

The current NumPy/SciPy core supports Python 3.10 or newer. The optional
ArviZ export currently needs Python 3.12 or newer. Older saved runs remain
loadable; compact histories created by the new code need the newer version to
resume. Release notes must explain the changed random streams and history
compatibility.

The [modernization roadmap](plans/modernization-roadmap.md) is the detailed
status tracker. The [workflow integration plan](plans/stage3-pipeline-features.md)
covers model adapters and posterior exports, while the
[ecosystem proposal](2026-09-08-ecosystem-integration.md) sets out how to
integrate the existing S-VBMC implementation, informed by the completed
backend comparisons. The
[original modernization discussion](2026-09-02-modernization-discussion.md)
retains the technical rationale and longer-term research ideas.
