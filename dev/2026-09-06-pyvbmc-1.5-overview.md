# PyVBMC 1.5: the big picture

*Release outline agreed on 6 September 2026; refreshed on 9 September 2026.*

PyVBMC 1.5 makes the existing VBMC method faster, more dependable and easier
to use in a broader modelling workflow. The NumPy/SciPy modernization, the
main correctness repairs and the model and posterior integration work are
implemented. A bounded PyTorch feasibility study is also complete. Its
evidence supports retaining the modernized NumPy core for this release. The PI
accepted that recommendation on 9 September 2026: PyVBMC 1.5 keeps the
NumPy/SciPy solver, with no full Torch solver port.

## What users should gain

**Faster runs and lower memory use.** PyVBMC now does less work between calls
to the user's model. Candidate evaluation, posterior-density calculations,
entropy and Gaussian-process integral work have been vectorized; GP prediction
and hyperparameter-sampling overhead have been reduced with GPyReg; and
expensive GP factors and optional noisy-acquisition details no longer inflate
ordinary optimization histories. The practical benefit still depends on how
much of a run is spent inside PyVBMC rather than evaluating the target.

| Measured outcome | Before | After | Change |
| --- | ---: | ---: | ---: |
| Total runtime across 280 benchmark runs | 9.92 h | 4.71 h | 2.11× speedup; 53% less time |
| Retained history, noisy logistic D=5, seed 0 | 117.3 MB | 4.6 MB | 96% less |
| Peak process memory, same noisy logistic run | 427 MB | 273 MB | 36% less |

The runtime row compares the pre-Stage-2 baseline with completed Stage 2 on
the same 14 configurations and 20 seeds, run by one worker with one BLAS
thread. The memory rows isolate the history repairs on the same trajectory.
These are historical laptop measurements: the cumulative runtime campaigns
used changed random streams and trajectories, although none of the 56
population comparisons was flagged. They do not measure the complete 1.5
release candidate, whose final integrated 870-run benchmark remains pending.
See the [benchmark plan](plans/benchmark-suite-and-golden-traces.md),
[modernization roadmap](plans/modernization-roadmap.md) and
[memory plan](plans/stage2-memory.md) for the full evidence.

**More reproducible and dependable inference.** Each run has its own seeded
random-number stream, shared throughout PyVBMC and GP fitting without changing
NumPy's global state. Saves retain the information needed to resume that
stream. Lower-precision inputs are widened consistently to float64, and the
parameter-transform, option and supporting-utility defects selected for 1.5
have been repaired.

The numerical campaign also repaired how the solver learns from past GP
hyperparameters, regularizes acquisition scores by predictive variance and
decides when to stop sampling GP hyperparameters. An unnecessary bound penalty
and its mutation of variational-optimizer parameters have been removed.
The final boost, which gives the fitted posterior one larger last refinement,
now removes a boost-only component-weight penalty and rejects a candidate when
either its estimated evidence or its uncertainty-adjusted score deteriorates
beyond the selected tolerance.
That guard is a score policy, not a claim that it always selects the more
accurate posterior: known beneficial rejections and harmful acceptances remain
part of the final population check.

**An easier route from a model to a fitted posterior.** Existing torch or JAX
models can be connected through a small adapter and an opt-in batch interface
for the initial design. The workflow supports ordinary and noisy targets,
supplied function values and separate scalar priors. Later active-sampling
calls remain sequential, because each selected point updates the GP before
the next one is chosen.

**An easier route from a fitted posterior to other tools.** `vp.to_torch()`
exports an independent distribution for sampling and differentiable density
evaluation, including bounded-parameter transformations and explicit dtype
and device choices. `vp.to_arviz()` exports named posterior draws using the
current ArviZ DataTree representation. Both integrations are optional; normal
NumPy/SciPy use requires neither torch nor ArviZ.

**A sound base for future methods.** The modernization gives future algorithm
work clearer numerical seams and stronger tests. Richer posterior families,
gradient-based acquisition optimization and larger-scale inference remain
separate research projects rather than promises of 1.5.

S-VBMC, which combines posteriors from several completed VBMC runs, has been
checked against the current code: all 32 upstream tests and checks of all 30
shipped real posteriors passed, including bounded stacking and optimization
for each posterior group. The PI endorsed making S-VBMC directly available
through PyVBMC and using it as the first example of a common delivery approach
for related methods. The existing S-VBMC algorithm is fully implemented in
its own repository; the remaining work is integration into PyVBMC.
The subsequent bounded optimized NumPy prototype matches S-VBMC's float64
outputs, gradients and optimizer behavior. Across eighteen paired complete
fits it is 2.47x faster than unchanged upstream S-VBMC. Giving Torch the same
optimized preparation narrows this to a median paired speedup of 1.06x
(1.15x aggregate), so much of the gain is shared implementation work.
This supports NumPy as a viable stacking implementation with fewer numerical
dependencies. The revised
[integration proposal](2026-09-08-ecosystem-integration.md) recommends
retaining Torch and the existing S-VBMC object workflow, with optional
dependencies and a migration route for current users. These recommendations
are for human review; production integration remains parked.
See the [prototype results](results/2026-09-09-svbmc-numpy-prototype.md)
for the timings, controls and limits of this three-example CPU study.

## Why we can make these changes confidently

The modernization adds finite-difference checks for the hand-derived
gradients, fixed MATLAB comparisons, stage-level numerical oracles and replay
of complete optimization trajectories. The benchmark collection covers
varied posterior shapes, dimensions and noise levels. These checks distinguish
intended numerical changes from ordinary run-to-run variation and provide
accuracy fences for changed trajectories.

The extended 870-run reference across 19 configurations is complete and
validated. The final-boost policy was studied through 1,740 paired boost arms
from those saved endpoints. These are reference and boost-only campaigns;
they do not replace the final integrated 870-run benchmark on the release
candidate after all correctness changes. That final campaign has not been run
and has no launch authorization.

The supported three-operating-system by three-Python-version matrix passed all
nine jobs after the main-loop changes. Variational stopping-rule research and
the separate GPyReg step-out issue are deferred work, not release blockers.

For the full numerical evidence and its limits, see the
[numerical-campaign summary](2026-09-08-numerical-campaigns.md).

## What the PyTorch feasibility study established

Stage 4 compared one complete variational fit using eager Torch, including
GP integrals, entropy, parameter handling, optimization, candidate selection
and final refinement sizes. It completed 96 bounded fits: 72 instrumented fits for
correctness and branch evidence and 24 tracing-free controls for performance.

The prototype showed useful float64 agreement for objective values and
gradients on fixed inputs. It also exposed differences in returned auxiliary
state and some accumulated drift over complete fits. The fixed-GP experiment
does not establish the speed or reliability of future Torch GP training or
its numerical retry behavior.

| Complete variational-fit measurement | NumPy CPU | Torch CPU | Synchronized CUDA |
| --- | ---: | ---: | ---: |
| Relative runtime across eight workloads | 1× | 2.12–6.26× | 3.35–23.34× |
| Sampled-GP final refinement, K=50 | 1.508 s | 3.932 s | 5.059 s |
| Synthetic D=15, N=750, K=50, one GP sample | 8.377 s | 29.446 s | 40.528 s |

These are single clean observations per workload and backend arm on one
Windows laptop, using one CPU thread and an RTX 4060 Laptop GPU. The float64
fits use fixed GP factors and include state preparation and required transfers.
Imports, CUDA context creation and warmup are timed separately. These are
variational-stage measurements, not full-solver timings or a universal backend
comparison.

The decision criteria remain joint: float64 values and gradients, numerical
reliability, acceptable CPU performance, synchronized GPU performance, setup
and transfer costs, implementation simplicity and installation impact. Around
1.2 times NumPy runtime was never an agreed cutoff, and GPU performance does
not replace the CPU requirement. Autodiff simplified parts of the backward
algebra, but preserving the estimator required substantial tensor, optimizer
and host-bridge machinery; the prototype did not demonstrate a net
implementation simplification. Its measured installation footprint and setup
costs add to the case for retaining NumPy in 1.5.

The PI accepted the recommendation on 9 September 2026: PyVBMC 1.5 keeps the
modernized NumPy/SciPy solver and will not receive a full Torch solver port.
The optional Torch and ArviZ posterior exports remain, and the existing Python
version floors do not change. Compilation, custom kernels, native Torch random
draws and Torch GP training were outside this study. The eager results did not
settle compiled-Torch feasibility. The subsequently authorized
[compiled follow-up](results/2026-09-09-torch-compile-follow-up.md) measures
compilation of the ordinary objective and backward pass, with fine scoring
kept eager and included in fit costs. It compares 80 complete fits across four
fixed-GP workloads. Warm medians below use three matched seeds per arm;
all times are seconds and CUDA work is synchronized.

| Workload | NumPy CPU | Eager Torch CPU | Compiled CPU | Eager CUDA | Compiled CUDA |
| --- | ---: | ---: | ---: | ---: | ---: |
| Deterministic D2/K1 | 0.00434 | 0.0188 | 0.00867 | 0.0756 | 0.0236 |
| Warped D5 | 0.274 | 0.722 | 0.574 | 1.16 | 0.406 |
| Sampled-GP boost D4/K50 | 1.48 | 3.94 | 3.16 | 4.48 | 1.19 |
| Synthetic boost D15/N750/K50 | 7.90 | 24.7 | 30.4 | 34.1 | 5.13 |

Compilation materially improves the GPU comparison: median paired warm
speedups over NumPy are about 1.28x and 1.54x on the two boost cases.
Compiled CPU remains roughly 2-4x the NumPy runtime by the per-arm medians; its largest
case varies from 21.3 to 31.8 seconds. Cold compiled first fits take 23-444
seconds on CPU and 12-122 seconds on CUDA, before separately reported setup.
These warm results assume reusable shapes and caches; they do not measure a
full run with a growing GP. A sampled-boost seed also shows endpoint parameter
drift despite small rescored ELBO differences. Full ranges, numerical gates,
setup requirements and limitations are in the detailed report. The evidence
improves the case for compiled GPU work but does not establish CPU acceptance;
the 1.5 NumPy/SciPy decision stands.

The complete design, timing table, numerical gates and installation evidence
are in the [Stage 4 feasibility plan](plans/stage4-torch-feasibility.md).

## What remains before release

1. Integrate the existing S-VBMC implementation for 1.5. Compatibility is
   complete; review the proposed code placement, preserved public workflow,
   optional dependency and migration contracts before integration work starts.
2. Settle the 1.5 placement of the proposed machine-local kernel calibration.
   Its API, cache and explicit recalibration behavior, wall-time and memory
   budget, and release placement remain open.
3. Add optional runtime hints to the 1.5 work list (PI, 2026-09-09;
   implementation deferred). Occasionally show one short, relevant tip at
   optimization startup, with repetition suppression, quiet-mode support and
   a separate disable option. Draw on the FAQ and planned user-facing skill;
   hint selection must not affect inference randomness or results. Frequency,
   repetition tracking and the precise option remain design choices; see
   [roadmap pickup 13](plans/modernization-roadmap.md#pickup-point).
4. Once the release candidate is frozen, explicitly authorize and run the
   final integrated 870-case population comparison, then complete the final
   documentation, release records and publication work.

The S-VBMC item records remaining release scope; the integration proposal
does not authorize production changes.

The planned user-facing `skills/pyvbmc/SKILL.md` remains part of the release
follow-up: FAQ/reference material, small helpers, and packaging and
installation guidance should be completed after the public API settles,
although FAQ drafting can begin earlier. See the
[user-agent skill proposal](2026-09-02-user-agent-skill.md).

The current NumPy/SciPy core supports Python 3.10 or newer. The optional
ArviZ export currently needs Python 3.12 or newer. Older saved runs remain
loadable; compact histories created by the new code need the newer version to
resume. Release notes must explain the changed random streams and history
compatibility.

The [modernization roadmap](plans/modernization-roadmap.md) is the detailed
status tracker. The [workflow integration plan](plans/stage3-pipeline-features.md)
covers model adapters and posterior exports, while the
[ecosystem proposal](2026-09-08-ecosystem-integration.md) sets out how to
integrate the existing S-VBMC implementation, informed by the completed
backend comparisons. The
[original modernization discussion](2026-09-02-modernization-discussion.md)
retains the technical rationale and longer-term research ideas.
