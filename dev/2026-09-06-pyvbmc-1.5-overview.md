# PyVBMC 1.5: the big picture

*Release outline agreed on 6 September 2026.*

PyVBMC 1.5 makes the existing VBMC method faster, more dependable, and easier
to use within a broader modelling workflow. The work completed so far
modernizes the NumPy/SciPy core. Whether a PyTorch implementation also
joins the 1.5 release is still to be decided.

## What users should gain

**Faster runs and lower memory use.** Reduce the work PyVBMC does between
evaluations of the user's model.

- Evaluate candidate points and posterior mixture components together,
  replacing costly Python loops with NumPy array operations.
- Speed up the posterior-fitting calculations, including entropy and
  uncertainty estimates, by sharing intermediate calculations and solves.
- Reduce overhead in training the Gaussian-process surrogate and sampling
  its hyperparameters, with corresponding improvements in GPyReg.
- Keep smaller optimization histories: store what is needed to reconstruct
  expensive GP state, avoid repeatedly copying past iterations, and make
  bulky diagnostic details optional.

The benefit depends on the problem and how much of the total time is spent
inside PyVBMC versus evaluating the model.

**More reproducible and dependable inference.** Make experiments easier to
repeat and fix known departures from the intended behavior.

- Give each run its own seeded random-number stream, used throughout the
  solver and GP fitting without changing NumPy's global random state.
- Preserve the random-number state when saving and resuming a run.
- Planned fixes: repair options whose intended behavior was inactive,
  including controls for GP sampling and acquisition regularization.
- Planned fixes: consistently widen lower-precision inputs to float64 and
  correct issues in parameter transformations and supporting utilities.
- Planned fix: keep the better posterior when the final refinement would
  otherwise make the solution worse.

**An easier route from a model to a fitted posterior.** Connect existing
torch or JAX models through a small, documented adapter.

- Provide adapter examples for ordinary and noisy model evaluations.
- Offer an opt-in batch interface for the initial design, so models can
  process the starting inputs together rather than through many calls.
- Support supplied function values and separate priors in that workflow.
- Keep one consistent interface for vectorized targets: later evaluations
  arrive as batches of one, while point selection remains sequential.

**An easier route from a fitted posterior to other tools.** Reuse the fitted
distribution for downstream analysis.

- `vp.to_torch()` exports a distribution for sampling and differentiable
  density evaluation, including the transformations for bounded parameters.
- The torch export is an independent snapshot with explicit precision and
  device choices, so it can be used without changing the original posterior.
- `vp.to_arviz()` exports independent posterior draws as current ArviZ
  DataTree data, with named parameters for analysis and plotting.
- Keep these exports optional for the NumPy/SciPy implementation: ordinary
  use requires neither torch nor ArviZ.

**Better connections to S-VBMC and upcoming extensions.** Make PyVBMC a
more convenient starting point for the wider family of VBMC methods.

- Planned: bring in or connect more closely to S-VBMC (Stacking VBMC),
  which combines the posteriors from several fitted VBMC runs.
- Check compatibility with existing posteriors and saved runs, and decide
  whether to include S-VBMC directly or provide clearer package integration.
- Make other upcoming VBMC extensions easier to connect to PyVBMC; their
  individual integration details remain to be defined.

## Why we can make these changes confidently

The modernization also builds a stronger validation foundation:

- Check mathematical derivatives against numerical approximations and keep
  agreement tests against MATLAB reference values.
- Save representative algorithm states and their expected outputs, making
  it possible to detect changes in individual calculations or precision.
- Replay complete optimization runs to see where their paths change.
- Compare inference quality over many random seeds and varied posterior
  shapes, dimensions, and noise levels; test supported Python versions
  across Windows, Linux, and macOS.

These checks help separate real regressions from ordinary variation. Bug
fixes may intentionally change results; the aim is to understand those
changes and validate the final release, rather than preserve every old result.

## What remains before release

The performance, random-number, and model/posterior integration work is
implemented. The remaining release path is:

1. Expand the benchmark reference using the completed modernization code.
2. Apply the planned correctness fixes and assess their effects.
3. Complete the S-VBMC integration and compatibility work, and establish
   the approach for connecting upcoming extensions.
4. Decide whether a PyTorch solver belongs in 1.5; if included, implement
   and validate it as part of the release work.
5. Validate the final code across the benchmark collection, then release 1.5.

## Compatibility and the next decision

- The current NumPy/SciPy core supports Python 3.10 or newer.
- The current ArviZ export needs Python 3.12 or newer.
- Older saved runs remain loadable; new compact optimization histories
  require the newer code to resume them.

**The solver implementation would be PyTorch, not JAX.** Its inclusion in
1.5 is an open decision, including any resulting dependency and Python
version changes. JAX support above refers to adapters for users' models;
a JAX implementation of the PyVBMC solver is not planned.
