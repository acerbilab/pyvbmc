## The first-question answer (items 4 and 5)

**The table of paths, row by row.** I rebuilt every row from the code and from a check, and every row of P2i's table holds. The initial design — the provided `x0`, the `plausible` draws, the `narrow` draws and the starting-cache rows the design consumes — reaches the target off the integer grid (`P2_4_integer_paths.py`, measured values quoted in row P2-4); each of the four search branches delivers a point on the grid, with the `D == 1` bounded search reaching exactly `x = 0.0`; a starting-cache row drawn by the sieve is snapped (and its stored value is then recorded at the moved point, which is P2i F1, the orchestrator's row); a chosen repeat is deliberately not snapped and the target sees the stored row itself. The snap is idempotent (200 random rows, `_real2int(_real2int(X)) == _real2int(X)`), which is what makes the comparison and the evaluation agree in the `cmaes` and `none` branches. The transformer question is settled by `vbmc.py:1405-1408`, which assigns `self.function_logger.parameter_transformer = self.vp.parameter_transformer` immediately before the call, so the two objects P2i names are the same object on entry; I read those lines.

**MATLAB on each path.** `misc/initdesign_vbmc.m` never calls `real2int_vbmc`: it warps `Xs` at `:49` and hands each row to `funlogger_vbmc` at `:51-58`, in both the `N0 <= Ns` branch and the k-means branch, and `misc/setupvars_vbmc.m:65` warps `x0` unsnapped. `private/activesample_vbmc.m` snaps in exactly three places: the search set at `:219`, the local search's starting point at `:248` (idempotent, since the set was already snapped) and the local search's result at `:325`. `misc/real2int_vbmc.m` returns early when no variable is an integer, inverts, rounds the integer columns with `round` (half away from zero) and warps back, writing only the integer columns. So MATLAB snaps the same three things PyVBMC snaps and leaves the same design unsnapped. Wave 4 recorded this in passing (`verification/wave4.md`, W4-2); it is now checked against the source line by line.

**What the documents say.** The option comment (`advanced_vbmc_options.ini:4`) describes the two accepted forms of `integer_vars` and the half-integer bound requirement; it is silent on the initial design and on `x0`. `docsrc/source/faq.md:431` says "No, VBMC does not support integer parameters (that is, variables forced to be integers — or, more in general, constrained to discrete values)", with a warning that simple workarounds may break VBMC's smoothness assumption. `CHANGELOG.md` has one "Integer variables" bullet under `Unreleased`, recording that a run with `integer_vars` and a search optimizer used to raise `IndexError` after its initial design, that such runs now complete, and that a coordinate exactly halfway between two integers is rounded away from zero as in MATLAB VBMC. The porting log and the user skill mention integer variables nowhere. MATLAB documents `IntegerVars` only as "Array with indices of integer variables" (`vbmc.m:194`); a grep of the whole `../vbmc` tree for "integer" turns up nothing else outside the code. **The contradiction is between (ii) and everything else**: the FAQ tells a user the feature does not exist, while the option exists, is checked at construction, is snapped through the search and has a changelog entry. The second, quieter gap is that no document says the first `fun_eval_start` evaluations are made off the grid, which is the part a user of a target defined only at integers has to know.

**The collision on a grid (item 5).** Confirmed and quantified in row P2-6. The essential numbers: two target calls at `x = 0.0`, `func_count 12 → 14`, `Xn 11 → 11`, no GP row added, `n_evals[0] 1 → 3`, and the in-loop update took `reupdate_gp` (the full recomputation) where a fresh point takes `gp.update` alone. MATLAB's `record` pools identically (`misc/funlogger_vbmc.m:229-247`), but MATLAB's `update1` is true there, so MATLAB appends a duplicate GP training row — already recorded as MATLAB-side defect 5 and as the reason the port deliberately differs. **There is no guard on either side** against acquiring an input that is already in the training set: `active_sample.py` has no membership test before the logger call, and MATLAB's only related code is the repeat block, which seeks repeats rather than avoiding them.

## Errors found in the reviewer's report

1. **F4, and the consequence it draws.** "The acquisition's own hard-bound mask (`abstract_acq_fcn.py:181-186`) cannot substitute: for an unbounded variable `lb_eps_orig = -inf + inf = NaN` …, every comparison against NaN is false, and the mask never fires." The premise is right and the conclusion is too broad. The mask is per coordinate: a **bounded** coordinate has a finite `lb_eps_orig`/`ub_eps_orig`, and a runaway transformed value inverse-maps onto the bound itself, which lies outside them, so the mask fires and returns `inf`. Measured: with bounds `[-10, 10]` on one coordinate, `inverse([[1e3, 1e3]]) = [[10.0, 6000.0]]` and the mask is `True`. The same correction applies to F4's consequence paragraph: "an acquisition that keeps improving in one direction drives the acquired point arbitrarily far outside the search box" holds for unbounded variables only.
2. **F7's consequence.** "`stop_timer` is not in a `finally`, so a target that raises leaves `fun_time` running and charges the whole interval to the next stop." The first half reproduces; the second does not follow. `timer.reset()` at `vbmc.py:1233` empties `_start_times` at the top of every iteration, and an exception from the target propagates out of `optimize` (nothing catches it between the logger and the caller), so there is no later stop to charge. The leak is bounded to its own iteration and has no observable consequence in any run — the same bound wave 1 established for the `gp_train` case.
3. **F3's reachability.** "Dormant at the shipped default (`search_cache_frac = 0`)." True of the search-cache consequences (b), (c) and (d), but not of (a): the two `np.delete` calls at `:467-468` run at every step at every option setting; they are simply without effect. And the option is not usable when turned on: with the shipped sieve fractions any `search_cache_frac > 0.25` makes the **second** active-sampling step raise `ValueError` (`P2_11`; `0.26`, `0.5` and `1.0` all fail, `0.1` and `0.25` do not). P2i's check ran one step with `0.5` and could not see this.
4. **F9(a) and F9(b), classification.** Both are presented as internal inconsistencies of the Python. Both are exact transcriptions of MATLAB: `cov(X)` against `cov(X_hpd,1)` at `activesample_vbmc.m:593`/`:596`, and the literal `3` at `:618-619`. (This is not a fault of an internal-track report, which did not read MATLAB, but the classification changes from "unsure" to "not a defect".) The same holds for F3(a)/(b), F8 and F10, each of which is line-for-line MATLAB.
5. **F2, a missing half.** "With the option on, nothing assigns it and `SearchAcqFcn[idx_acq]` at `:408` raises." Exactly right for the Python. What the report could not say, and what changes the disposition, is that MATLAB assigns `idxAcq` only when `numel(SearchAcqFcn) > 1`, so a MATLAB run with `AcqHedge` and the default single `@acqf_vbmc` fails in the same way; PyVBMC's defect is the broader one, not a wholly new one.

7. **Coverage.** "`pyvbmc/testing/vbmc/test_vbmc_active_sample.py` (all 2246 lines)" — the file has 2245 lines and ends with a newline. Trivial, recorded for completeness.
