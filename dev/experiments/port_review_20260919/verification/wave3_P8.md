## Errors found in the reviewers' reports

**P8 internal.**
1. **F12, test adequacy — the central factual error of the pair.** "`test_handle_0D_1D_input_decorator.py` has eight tests covering 1-D and 2-D inputs, keyword and positional, tuple and scalar returns — and not one 0-D input, despite the decorator's name." The module has **14** tests, and **8** of them are named `test_0D_*` and do pass a 0-D input (`x = 1`). They assert exactly the behaviour F12 calls a defect — `test_0D_kwarg`/`test_0D_posarg`/`test_0D_return_multiple_returns` assert the result is `(1, 1)` — so the tests **pin** the non-unwrapping rather than miss it, and `test_0D_return_scalar` passes only because `np.sum(x)` is already 0-D before the decorator declines to touch it. The rest of the note stands: no test omits the patched argument, and none patches two arguments (`test_0D_multiple_*` have two *arguments*, one *patched*).
2. **F5.** "The repeat-candidate set (`active_sample.py:403`) is drawn from `function_logger.X[X_flag]`, so it never offers a dead row" — right for one iteration, but it misses the route that makes the finding reachable at all: `optim_state["search_cache"] = X_search[inds]` (`:432`) stores the whole ranked candidate set, training points included, and that cache is read in the *next* iteration (`:946-962`), i.e. possibly across a warm-up trim. Both enabling options default to 0, so the conclusion ("reachability in a real run is low") survives, with a sharper condition.
3. **F8.** "Either the comment names a reset the code does not perform, or the reset is in the wrong place." The comment *and* the three-line reset are `misc/warp_input_vbmc.m:164-167` verbatim; the block is a faithful port, and the mixing of pre- and post-warp hyperparameter statistics it points at is shared by MATLAB. (The internal track did not read MATLAB, so this is a limitation of the track rather than a misreading.)
4. **F9.** "the term should be `np.log(np.abs(scale))`" is right as a repair, but the report does not know that `np.log(self.scale)` is MATLAB's own expression (`warpvars_vbmc.m:764`); only the missing validation is a Python choice.
5. **F4.** "`total_fun_eval_time` stays correct" is true in the NaN case, but the report misses the other half of the same asymmetry that P8c F7 found: `add` with an explicit time charges the total, where MATLAB's `'add'` never touches it.

**P8 comparison.**
6. **F8, consequence.** "none inside PyVBMC — `active_sample.py:696` discards the value and uses `idx_new`". Wrong: line 696 binds `ynew`, and `:808` does `ynew = np.array([[ynew]])` before `gp.update`. What keeps the `(1,)` shape from reaching gpyreg is the `update1 = n_evals[idx_new] == 1` guard at `:803`, which P8 internal F13 identifies correctly.
7. **F7, consequence.** "`total_fun_eval_time` feeds `results["overhead"]`, which PyVBMC already returns as NaN". Wrong on the mechanism: `output["overhead"] = np.nan` is a literal at `vbmc.py:3293` and reads nothing; the only reader of `total_fun_eval_time` in the package is `FunctionLogger.__str__`. 8. **F7, test adequacy.** "nothing checks the default or a repeated `add`". Half wrong: `test_add_record_funtime` (`:96-104`) does exercise the NaN default on a fresh row (`f_logger.add(x * 3, y, None)`) and asserts both `total_fun_eval_time == np.nansum(fun_eval_time)` and `== 20`. 9. **F6, trigger.** "A NaN correlation needs a zero (or non-finite) diagonal entry of the variational covariance". A **zero** diagonal entry does not make the two maskings differ (`p8_corr_mask.py`): the NaN entries of `vp_corr` then sit where `vp_cov` is already zero, and the remaining entry is `±inf`, which both sides keep. The maskings differ only for a **negative** or **non-finite** diagonal entry.
10. **F5, history.** "the Python code had types 1 and 2 until commit `6a247e59`". The behaviour was the identity before and after; `6a247e59` removed dead labels, not a working transform. 11. **F1, quoted numbers (minor).** `29.148 / 10.381 / 15274.55` are for `lb=-5, ub=5` **with** `plb=-1, pub=2`; the same point with no plausible bounds gives `36.737 / 8.2095 / 12821.17`. The qualifier is missing from the finding.
