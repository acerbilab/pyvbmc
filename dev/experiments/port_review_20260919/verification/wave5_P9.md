## The check of the first-question answers (item 12)

Both reports answer the same first question — does each sampler draw from the density its own density function defines? — and both answer yes. I re-derived the claim from the sources rather than from the reports, and it holds on both sides, with one qualification and one correction to a supporting number.

**The rejection samplers' envelope.** `Trapezoidal.sample` and `SplineTrapezoidal.sample` bound the density by `y_max = pdf(0.5*(u+v))` and accept a proposal when `z1 <= y1` with `z1 ~ U(0, y_max)` (`trapezoidal.py:149-169`, `spline_trapezoidal.py:153-173`); `mtrapezrnd.m:48-68` and `msplinetrapezrnd.m:48-68` are the same scheme. `0.5*(u+v)` lies on the plateau whenever `u < v`, and the plateau is the maximum of both families, so the envelope dominates. I checked it rather than assumed it: over 300 random argument sets per class (four sorted uniforms on `[-20, 20]`), the largest relative excess of the maximum of the density on a 20 001-point grid over the envelope height is **exactly 0.0** for both classes, and on three deliberately extreme sets — a plateau of width 1e-8 in a box of width 10, a plateau pushed against the upper bound, and `(-1e6, -1, 1, 1e6)` — the envelope and the grid maximum agree to six significant figures. So the envelope is the maximum for every valid argument, and the acceptance rate is `1/(y_max·(b-a))`, never worse than 1/2 for the trapezoid.

**The smooth-box mixture weights.** `SmoothBox.sample` draws `u ~ U(0, nf)` with `nf = 1 + (b-a)/(√(2π)σ)` and takes the left half-normal for `u < 0.5`, the right for `0.5 <= u < 1` and the plateau for `u >= 1` (`smooth_box.py:120-145`), which is `msmoothboxrnd.m:48-73` line for line. The implied weights are `0.5/nf` per tail and `(nf-1)/nf` for the plateau; the exact masses are `Cσ√(2π)/2` and `C(b-a)` with `C = 1/((b-a) + √(2π)σ)`. They agree to every printed digit on four settings spanning the regimes (`(0,1,1)`: 0.357413 against 0.357413 and 0.285174 against 0.285174; `(-5,5,0.1)` and `(0,100,1)`: 0.012227 and 0.975547; `(0,1e-3,5)`, a plateau 8e-5 of the mass: 0.499960 and 0.000080), and 400 000 draws reproduce them (empirical plateau fractions 0.2848, 0.9756, 0.000070, 0.9756).

**Normalizers with parameters that differ across dimensions.** With `a = [-3, 0, 10]`, `u = [-2, 0.5, 11]`, `v = [1, 0.75, 18]`, `b = [2, 4, 20]`, `scale = [0.2, 1, 5]` — every parameter different in every dimension — the product of the three marginal integrals by `scipy.integrate.quad` is 1.0 (`UniformBox`), 1.0 (`Trapezoidal`), 0.9999999999823744 (`SplineTrapezoidal`) and 0.9999999999331113 (`SmoothBox`, over `±40σ` beyond the pivots); and the `D = 3` density equals the product of its marginals to 7e-18 on a 729-point grid, so the families really are separable and the normalizer really is per dimension.

**Kolmogorov–Smirnov, both sides.** I derived closed-form CDFs for the four families by hand and checked each against quadrature of the code's own `pdf` (max errors 1.1e-16, 1.1e-16, 1.7e-11, 2.4e-10), then tested every sampler against them at n = 200 000, PyVBMC's and my MATLAB transcription's side by side: `UniformBox(-3,2)` p = 0.588 / 0.034; `Trapezoidal(0,.25,.75,1)` 0.614 / 0.316; `Trapezoidal(0,.01,.02,10)` (rejection rate ≈ 1/2) 0.882 / 0.379; `SplineTrapezoidal(0,.25,.75,1)` 0.350 / 0.329; `SplineTrapezoidal(0,.01,.02,10)` 0.702 / 0.238; `SmoothBox(0,1,1)` 0.218 / 0.024; `SmoothBox(-5,5,.1)` 0.341 / 0.548. ## Errors found in the reviewers' reports

1. **P9i F3** presents the three-way disagreement at a NaN coordinate as a PyVBMC property ("Three different answers to the same question", classified "suspected defect"). All four answers are identical in MATLAB: `munifboxlogpdf.m:51` uses the same two comparisons and returns the full density at NaN, and the other three MATLAB log-densities return `-inf`. The property is shared, not a port difference. (The internal-track reviewer did not read MATLAB, so this is a limit of the track rather than a misreading; it changes the classification.)
2. **P9i F4**: "a density that is `-inf` (zero) **everywhere**" for `Trapezoidal(0, nan, 0.75, 1)`. It is `-inf` outside `[v, b)` and **NaN** on `[v, b)`, because the normalizer itself is NaN — measured, and identical in MATLAB.
3. **P9i F4** and **P9c F4** both frame the permissive NaN/infinity handling as a PyVBMC property. MATLAB's own checks (`munifboxlogpdf.m:44`, `msmoothboxlogpdf.m:26`, `:46`) are the same comparisons and pass NaN identically, and `mtrapezlogpdf.m`/`msplinetrapezlogpdf.m` have no order check at all. My transcription of `mtrapezrnd` at a NaN pivot is uniform on `[a,b]`, exactly as PyVBMC's sampler is.
4. **P9i F2** lists `smooth_box.py:79` with the two trapezoids for the `INT64_MIN` fill. `SmoothBox`'s three branches partition the real line, so the fill is always overwritten and the smooth box leaks only the dtype (truncation, and float32 in, float32 out); it never returns `INT64_MIN` or a wrapped value.
5. **P9i F2** understates the consequence. Besides "density 1" for an even number of out-of-support coordinates, a mix of in- and out-of-support integer coordinates can wrap to a large **positive** int64 and give `pdf = +inf`: `Trapezoidal(0,2,8,10,D=3).log_pdf([[20,5,5]])` is `+9223372036854775804`. And `Product` never reproduces the wrap at all, because it accumulates into a float64 array (measured `-1.84e19` → pdf 0).
6. **P9c F5**: "a window in which another thread's `np.seterr(divide='raise')` is silently disabled", and the suggestion that `np.errstate` would be "thread-local in intent". NumPy's error state is already per thread — measured: a child thread saw the default `warn` while the main thread held `raise`, and the child's `ignore` left the main thread at `raise`. The leak from the missing `try`/`finally` is real but confined to the calling thread. P9i F8's hedged "(or thread)" stands.
7. **P9c F4, test adequacy**: "they would not let the check be relaxed without being edited." Both error-handling tests use `u[1] = 0.9` against `v = 0.75`, a strict violation, so relaxing the pivot comparisons from `>=` to `>` leaves them green.
8. **P9c F3, history**: "The `isinstance(marginal, UserFunction)` special case in `sample` was added by `d02c517e` ... the density path was not given the matching case." True as far as it goes, but it reads as though the asymmetry began in 2026.
