## 2. First question — the log predictive density, and which noise each output adds

**Is `lpd` the log density of `y_star` under the predictive distribution of an *observation*, i.e. with latent + noise variance?** Yes, in every combination I could construct, and this is the one quantity `lpd` ever returns.

- Per sample (`separate_samples=True`): `gaussian_process.py:2036–2040` uses `y_s2[:, s]`, set at `:2032` to `s2_latent + sn2_star·sn2_mult`. Checked against `scipy.stats.norm.logpdf(y_star, mu_s, sqrt(y_s2_s))` for all three PyVBMC noise parameterizations (constant; constant + user-provided; constant + scaled user-provided), with and without `s2_star`, one and three hyperparameter samples: max |difference| 4.4e-16 (`e3`).
- Averaged (`separate_samples=False`): `lpd = log N(y_star; mu_bar, mean_s(y_s2_s) + v)` with `v = var_s(mu_s, ddof=1)`, i.e. the moment-matched Gaussian of the mixture, not `log (1/S) Σ_s N(y_star; mu_s, y_s2_s)`. On my 20-point 2-D example the two differ by up to 1.7e-3 nats. The docstring covers this ("returns the lpd of the corresponding mean approximation"), though it does not name the moment matching.
- `add_noise` does not change `lpd`: with `add_noise=True` the averaged branch reads the already-averaged `y_s2` through `s2`, with `add_noise=False` it averages `y_s2` separately, and the two are the same number (`np.allclose` true in all 12 combinations of `e3`). So the noise is *always* in `lpd` while the returned `s2` is latent unless `add_noise=True`; a caller who reads "add_noise defaults to False" may not expect that (minor observation M2).
- `s2_star` enters `lpd` exactly through the noise function, i.e. only in the parameterizations that declare a user-provided feature; with `user_provided_add` off it is silently ignored (M7).

**Which noise variance does each noise-inclusive output add at a test point?** All three go through `GaussianNoise.compute(hyp_noise, x_star, y_star, s2_star)`, which returns `exp(2h₀)` (or `np.spacing(1)` if `constant_add=False`) `+ s2_star` (feature value 1) or `+ exp(h₁)·s2_star` (feature value 2, `s2_star = 0` when `None`) `+ exp(2h_{i+1})·max(0, h_i − y_star)²` (output-dependent, dropped without `y_star`). Then:

- `predict` (`:2032`): `s2_latent + sn2_star · sn2_mult`. Consistent with the fit, which factorizes `K + sn2_mult·diag(sn2(X, y, s2))` with the same function on the training points — confirmed at `sn2_mult = 10` and `10⁷`, where the added term was exactly `sn2·sn2_mult` and the latent variance came from the inflated matrix (`e12`).
- `predict_full` (`:1852`): the same `sn2_star·sn2_mult`, but added as `np.dot(np.eye(N), sn2_star)`, which is a *column vector* when `sn2_star` is per-point — **F1**.
- `quad`: adds no noise at all, which is right for the integral of the latent function; the noise enters only through `sn2` when it recomputes `sl` — and that recomputation is **F2**.

So the `sn2_mult` of a retried factorization is carried correctly everywhere it is used, and the parameterizations are consistent between training and test points. The two defects are in *how* the noise is applied (`predict_full`) and in the factorization scale `quad` derives from it.

## 3. Findings

### F1. `predict_full(add_noise=True)` adds per-point noise to whole rows instead of the diagonal
- Location: `gpyreg/gaussian_process.py:1852`; MATLAB: "not read (internal track)"
- Category: indexing/shape
- Proposed classification: suspected defect
- Confidence: high
- The line is `cov[s, :, :] += np.dot(np.eye(N_star), sn2_star) * sn2_mult`. When the noise function returns a scalar (no user-provided and no output-dependent feature) `np.dot` degenerates to multiplication and the result is `sn2·I`, correct. When it returns an `(N*, 1)` array — any `s2_star` vector under `user_provided_add`, or output-dependent noise with `y_star` — `np.dot(eye(N*), sn2_star)` is the matrix product `(N*,N*) @ (N*,1) = (N*,1)`, and `+=` broadcasts that column across the columns of `cov[s]`, adding `sn2_star[i]` to *every* entry of row `i`. The model requires `diag(sn2_mult·sn2_star)`: observation noise is independent across test points. The diagonal comes out right, so `predict_full` still agrees with `predict`, but every off-diagonal entry is polluted and the matrix is no longer symmetric (the "enforce symmetry" step at `:1840` runs *before* the noise is added).
- Consequence if real: the returned matrix is not a covariance — asymmetric and in general not positive semi-definite — so anything that factorizes it, inverts it, or reads a cross-covariance from it is wrong. Magnitude is the full noise variance in each off-diagonal entry (0.0125 to 0.1625 on my example, against latent covariances of order 1e-3). Triggers only with heteroskedastic test-point noise. **Not reached by a default PyVBMC run**: PyVBMC production code never calls `predict_full`, and the two PyVBMC test helpers that do (`pyvbmc/testing/acquisition_functions/_look_ahead.py:27`, `pyvbmc/testing/acquisition_functions/test_acq_fcn_viqr_losses.py:115`) pass neither `s2_star` nor `add_noise`.
- Suggested reproduction: `e1_predict_full.py`. `cov(add_noise=True) − cov(add_noise=False)` came out as four constant rows `[0.0125…]`, `[0.0425…]`, `[0.0925…]`, `[0.1625…]` instead of a diagonal; symmetry check `False`. With `s2_star=None` the difference was exactly `0.0025·I`.
- Test adequacy: no. No test in gpyreg passes a nonzero vector `s2_star` to `predict_full`; the only `s2_star` arrays in the suite are the zero vectors of the two `test_predict_lpd` copies and the `predict` call in `test_predict_cross_covariance.py:239`.

### F2. `quad(compute_var=True)` recomputes the factorization scale `sl` instead of using the stored one, and the integral variance collapses after a rank-one update
- Location: `gpyreg/gaussian_process.py:2188–2196` (`sl = np.min(sn2) * self.posteriors[s].sn2_mult`), used at `:2234`; the stored value is `Posterior.sl` (`:2928–2933`), set at `:2843` and preserved by the rank-one update at `:863–865`, `:910–918`
- Category: state/caching (with a formula consequence)
- Proposed classification: suspected defect
- Confidence: high
- `invKzk` must be `inv(K + sn2_mult·diag(sn2))·zᵀ`, and since `L` factorizes that matrix *divided by the scale it was built with*, the division at `:2234` must use exactly that scale. `quad` instead derives it afresh from the current training noise. `Posterior.sl` exists precisely because the two can differ: its own docstring says "Rank-one updates extend the factorization with this scale, so it can differ from the minimum of the current training noise after observations have been appended", and `update` appends `1/sqrt(sl)` to `sW` and `u/sl` to `L` using the *stored* `sl` (`:863`, `:912`). Whenever an appended point has a smaller total noise than every earlier point — which the release notes describe as the ordinary case, "points added without `s2_new` to a GP that stores `s2` … get a variance of zero" — the recomputed `sl` is smaller than the stored one, `invKzk` is inflated by their ratio, `J_kk` goes negative, and `np.maximum(np.spacing(1), J_kk)` at `:2239` returns machine epsilon. This is the same failure the 1.2.1 release note reports as fixed for heteroskedastic noise ("previously collapsed to machine epsilon"), reachable again by a different route.
- Consequence if real: the integral variance is silently reported as 2.2e-16 instead of its true value, i.e. total confidence in the quadrature estimate; with a milder ratio the variance is merely too small. The mean is unaffected. **Not reached by a default PyVBMC run** — PyVBMC never calls `quad` (`_gp_log_joint` reimplements it) — but PyVBMC *does* take the rank-one path inside active sampling, so a user script that calls `quad(compute_var=True)` on a GP taken from a PyVBMC run hits it; likewise any standalone use of `update` with one new point.
- Suggested reproduction: `e2_quad.py`, section C. A 14-point GP with `s2 = 0.05` everywhere and constant noise `1e-3` has `sl = 0.050001`; after `update(X_new=one point, s2_new=0.0)` the stored `sl` is unchanged while `min(sn2)·sn2_mult = 1e-6`. `quad(0.3, 0.7, compute_var=True)` then returns `var = 2.220446e-16`, where a full recomputation on the same data and hyperparameters gives `6.430155e-03` and Gauss-weighted quadrature of the rank-one GP's own `predict_full` gives `6.430155e-03` (so the extended factors are right and only `quad`'s scale is wrong). The means agree to all digits.
- Test adequacy: no. `test_quadrature_without_noise`, `test_quadrature_with_noise_matches_numerical_integration` (three parameterizations) and `test_quadrature_with_noise_fitting` are genuine specification tests against Gauss–Hermite quadrature of `predict_full`, but every one of them calls `quad` on a freshly computed posterior; none calls it after an `update` that appends a point.

### F3. The eigendecomposition fallback of `random_function` returns a factor of the wrong covariance
- Location: `gpyreg/gaussian_process.py:2619–2622` (inside `__robust_cholesky`), reached from `random_function` at `:2593`
- Category: indexing/shape
- Proposed classification: suspected defect
- Confidence: high
- The intent of `maxidx = np.argmax(np.abs(U), axis=0)` / `negidx = U[maxidx] < 0` / `U[negidx] *= -1` is to give each eigenvector a positive largest-magnitude entry, a sign convention that would leave `Tᵀ T` unchanged. But `maxidx` is one row index *per column*, and `U[maxidx]` is fancy indexing on axis 0, so it is an `(N, N)` matrix whose row `k` is `U[maxidx[k], :]`; the comparison yields an `(N, N)` mask and `U[negidx] *= -1` flips individual entries, which destroys the orthogonality of the columns. `T = diag(sqrt(D)) @ real(U[:, t]).T` then satisfies `Tᵀ T ≠ sigma`. (Two further weaknesses in the same block: `sp.linalg.eig` is used on a symmetric matrix where `eigh` is the right routine — I observed it return eigenvectors with imaginary parts up to 0.24 for a rank-deficient symmetric matrix, which `np.real(D)`/`np.real(U)` then silently truncate; and when any kept eigenvalue is negative the function returns an all-zero `T`, so the draw silently loses its randomness instead of raising.)
- Consequence if real: `random_function` returns draws with the wrong joint distribution whenever the predictive covariance is numerically singular — repeated or near-duplicate test points, or test points that coincide with training points at low noise. Marginal variances stay roughly right, so the error is easy to miss; the correlations are not. **Not reached by a default PyVBMC run** (nothing in PyVBMC calls `random_function`).
- Suggested reproduction: `e5_signblock.py` isolates the block — on a rank-2 5×5 PSD matrix, `max |TᵀT − sigma|` is 5.50 with the flip and 2.2e-15 without it (or with a per-column flip), and the mask printed as a non-uniform `(5,5)` boolean array. `e6_rf_fallback.py` shows it end to end: with `Xs = [[0],[0],[1],[1],[-1.5]]` the plain Cholesky fails, and the empirical covariance of 6000 `random_function` draws has the *opposite sign* off the diagonal from `predict_full`'s (the two identical test points come out with correlation −0.76 where it must be +1). `e4` confirms that on generic test points, where the Cholesky succeeds, the draws are correct.
- Test adequacy: no. `test_random_function` and `test_fit_and_random_function_with_generator` draw at generic points, where the direct Cholesky always succeeds; the fallback has no test of its own, and none of the three `__robust_cholesky` tests I looked for exists.

- Location: `gpyreg/covariance_functions.py:414` (`plausible_upper_bounds[D] = 5.0`, in a block whose other three lines write `[-1]`)
- Category: indexing/shape
- Proposed classification: suspected defect
- Confidence: high
- The kernel has `cov_N = D + 2` hyperparameters, `D` lengthscales, then the log output scale at index `D`, then the log shape at index `D + 1 = -1` (`hyperparameter_info`, `:303–308`). The block at `:411–415` sets the shape parameter's `LB`, `UB`, `PLB` and `x0` through `[-1]` but its `PUB` through `[D]`. The effect is two errors in one line: the output scale's plausible upper bound, set to `log(height)` at `:406`, is overwritten with the constant 5.0, and the shape parameter's plausible upper bound is left at the `+inf` of the initialization.
- Consequence if real: the plausible box that seeds the space-filling design is wrong for two hyperparameters. `fit` intersects `PUB` with `UB` (`:1196`), so in practice the output scale's plausible upper bound becomes its hard bound `log(10·height)` instead of `log(height)`, and the shape parameter's becomes its hard bound 5 instead of a plausible value — both plausible ranges widen, so the initial design and the sampler widths are drawn from a coarser box. - Test adequacy: no. `test_rational_quad_ard_checks`, `test_cov_rational_quad_ard`, `test_simple_rational_quad_ard` and `test_rqard_kernel_gradient` cover `compute` and its gradient only; no test in the suite reads `PLB`, `PUB` or `x0` from any component (`test_setting_bounds` compares only `LB` and `UB`, and only against the components' own return values).

### F5. The isotropic bound helper takes `min`/`max` of a scalar, so both lengthscale bounds use the mean width
- Location: `gpyreg/isotropic_covariance_functions.py:233–245`
- Category: control flow (dead computation)
- Proposed classification: suspected defect
- Confidence: medium
- `width = np.mean(np.max(X, axis=0) - np.min(X, axis=0))` is already a scalar, so `min_width = np.min(width)` and `max_width = np.max(width)` are both that same mean and the two names describe nothing. The names, and the asymmetric use (`min_width` for the lower bounds, `max_width` for the upper), say the intent was to bracket the single isotropic lengthscale between the narrowest and the widest dimension, which requires the per-dimension vector `np.max(X, axis=0) - np.min(X, axis=0)`. As written the bracket is the mean width in both directions. I call it medium rather than high because "the mean width both ways" is a defensible recommendation on its own; what is not defensible is computing `min` and `max` of a scalar.
- Consequence if real: the recommended and plausible bounds on the isotropic log lengthscale are narrower than intended, and on data whose dimensions differ in scale they can exclude the sensible value entirely; the effect grows with the spread of the per-dimension widths. Bounds only, no direct effect on the arithmetic. **Not reached by a default PyVBMC run** (the isotropic kernels are a Python-only addition that PyVBMC does not use).
- Suggested reproduction: `e7_bounds.py`. With widths `[0.912, 935.07]`, `LB[0] = -7.667 = log(mean)+log(tol)` where `log(min)+log(tol) = -13.907`, and `UB[0] = 8.451 = log(10·mean)` where `log(10·max) = 9.143`.
- Test adequacy: no. `test_gaussian_process_isotropic.py` exercises `LB`/`UB` only through the same `get_recommended_bounds` mirror as the ARD case.

### F6. The recommended starting value for per-dimension length scales and mean-function widths is a pooled scalar standard deviation
- Location: `gpyreg/covariance_functions.py:451` (`plausible_x0[0:D] = np.log(np.std(X, ddof=1))`), `gpyreg/mean_functions.py:524` (`x0[1 + D : mean_N] = np.log(np.std(X, ddof=1))`), `gpyreg/isotropic_covariance_functions.py:246`; MATLAB: "not read (internal track)"

- Proposed classification: possibly intentional
- Confidence: medium

The consequence of the mismatch is not only a poor start but an *inconsistent* one: the pooled value can lie outside the per-dimension bounds the same call returns.
  This names the known-differences entry **"NumPy quantile and standard-deviation conventions in GP bound recommendations"** (Slices G1/G2/P5), which cites `mean_functions.py:522-523` and rests on the code comment "note that std behaviour in MATLAB and NumPy is slightly different". The entry's own description covers only interpolation conventions (`np.quantile`'s `(i-1)/(N-1)` against `quantile1.m`'s `(i-0.5)/N`) and says nothing about a pooled scalar standing in for `D` per-dimension values; on the evidence of the code the `ddof=1` argument *is* the convention the comment was written about. I report it so that the settled-difference entry can be either widened to state this explicitly or corrected.

- Suggested reproduction: `e7_bounds.py`. On `X` with dimension 0 in `[0,1]` and dimension 1 in `[0,1000]`, the per-dimension standard deviations are `[0.271, 259.3]` while `x0[0:2] = log(338.9) = 5.826` for both; `x0` lies outside `[LB, UB]` (`UB[0] = 2.211`) and outside `[PLB, PUB]`.

### Minor observations

- **M1.** `predict_full`'s docstring says `add_noise : bool, defaults to True` (`:1773`) while the signature default is `False` (`:1759`). The 1.2.0 release notes record this same correction for `predict` but not for `predict_full`, and the docs page autodocs the docstring, so the published reference is wrong.
- **M2.** `predict`'s summary line ("Compute the GP posterior mean and noise variance at given points") and its `s2` description ("Noise variance at each point") describe the `add_noise=True` output, while the default is the latent predictive variance. Relatedly, `lpd` always carries the observation noise even with `add_noise=False`, which the docstring does not say (see the first question).
- **M3.** `AbstractKernel.compute`'s docstring (`covariance_functions.py:44–46`) says the return is "(N,)" when `compute_diag=True`; all five implementations return `(N, 1)`, and `predict:1994` indexes the result with `[:, 0]`, which raises `IndexError` on a 1-D array. A custom kernel written to the published contract would break `predict`. The docstring, not the code, is what I would call wrong here.
- **M4.** `predict:2049` and `quad:2248` compute the across-sample spread of the means with `ddof=1`. The moment-matched variance of the equally weighted mixture is `mean(s2) + (1/S)Σ(mu_s − mu_bar)²`, so the returned variance is inflated by `S/(S−1)` on that term (11% of the spread term at 10 hyperparameter samples). The two sites agree with each other, and this looks like the MATLAB `var(...,[],2)` convention rather than an oversight — flagging it for the comparison reviewer. It does reach a default PyVBMC run: `vbmc.py:1644` and `:2543` take `sqrt(f_s2)` from an averaged `predict` to form `lcb_max`, which drives the end of warm-up.
- **M5.** `random_function(add_noise=True)` calls the noise function as `noise.compute(hyp_noise, X_star, None, None)` (`:2600–2602`), so under `user_provided_add` it silently drops the user-provided term (there is no `s2_star` argument to pass) and under output-dependent noise it drops that term as well, although the freshly drawn `f_star` is exactly the `y` that term is defined on. The drawn observation is then under-dispersed with no warning.
- **M6.** `predict(add_noise=True)`/`predict_full` with output-dependent noise and `y_star=None` silently omit the output-dependent component (`noise_functions.py:269`, `if y is not None`), rather than raising as they do for `return_lpd` without `y_star`.
- **M7.** `s2_star` is silently ignored when the noise function declares no user-provided feature (`noise_functions.py:258–266`), and symmetrically a GP declared with `user_provided_add=True` but never given `s2` trains on the constant term alone. Both are quiet.
- **M8.** `quad` has no guard for a prior-only GP: `N, D = self.X.shape` raises `AttributeError: 'NoneType' object has no attribute 'shape'` where `predict` handles that case and returns the prior. Its `mu`/`sigma` handling also accepts only `(N, D)` arrays or scalars — a 1-D array of length `D` is read as `D` separate 1-D measures and raises `IndexError` for `D > 1`. Both are documented-input violations, but the errors point nowhere near the cause.
- **M9.** Degenerate training sets produce infinite or inverted recommended bounds with no diagnostic: with constant `y`, `GaussianNoise.get_bounds_info` returns `UB = -inf` against `LB = -13.8` (so `LB > UB`) and the covariance output scale gets `LB = UB = -inf`; with a single 1-D training point the length-scale `x0` is `-inf` (rescued only incidentally by the NaN-midpoint fill at `:460–463`, which does not catch `-inf`). `e13_edges.py`.
- **M10.** `SquaredExponential.compute(compute_diag=True, compute_grad=True)` returns an `(N,1)` value and a full `(N,N,cov_N)` gradient built by broadcasting that column — a meaningless combination that is neither rejected nor documented (`covariance_functions.py:161–193`). No caller uses it.
- **M11.** `predict` clips negative variances (`:2023`) and `predict_full` does not, so their diagonals can differ by the clipping on a numerically singular posterior. Defensible (a full matrix cannot be clipped entrywise), worth knowing when comparing the two.
- **M12.** With `constant_add=False` the noise function returns a hidden `np.spacing(1.0)` nugget (`noise_functions.py:251`) that the class docstring ("the independent contribution of each noise feature") does not mention; it is also what decides `L_chol = min(sn2) >= 1e-6` for such a GP.
- **M13.** `_convert_shapes` accepts a Python `int`/`float` `s2` but rejects a NumPy integer scalar (`np.int64(3)` raises `TypeError`, since `np.float64` subclasses `float` and `np.int64` does not) — `gaussian_process.py:2877–2887`. It also raises `AssertionError` for shape problems where the rest of the module raises `ValueError`, and the two messages lack a space (`"input data {D}" "doesn't match"`).
- **M14.** The isotropic kernels have no `docsrc` page: `docsrc/source/covariance_functions.rst` documents `AbstractKernel`, `RationalQuadraticARD`, `Matern` and `SquaredExponential` only, so `SquaredExponentialIsotropic` and `MaternIsotropic` are absent from the published reference although `AbstractIsotropicKernel` carries full numpydoc.
- **M15.** `quad`'s docstring has "conputed" (`:2107`), and the stale comment `# sigma doesn't work, requires gplite_quad implementation` sits at `:2257` above `plot` although `quad` exists.

## 4. Test adequacy notes

- **`test_predict_lpd` (`test_gaussian_process.py:1206`) and its isotropic twin (`test_gaussian_process_isotropic.py:1045`) test a different model than their comments describe, and neutralize their own assertion.** The GP is built with `GaussianNoise(user_provided_add=True)`, whose `hyperparameter_count()` is 0, so the ARD GP has `4 + 0 + 7 = 11` hyperparameters — but each row of `hyp` has 12 entries. `update(hyp=...)` on a GP with no data stores the row without validating its width (`gaussian_process.py:983–994`), so `predict` reads `hyp[4:11]` as the mean block: the intended noise hyperparameter `log(pi) = 1.1447` becomes the negative quadratic's `m0`, `-(D/2)log(2pi) = -2.757` becomes the first mode location, and the twelfth entry is never read. The isotropic copy is further off, since `cov_N = 2` there: only 9 of its 12 values are read at all, and the intended `log sf2 = 1.0` is not among them. Then `s2_star = np.arange(-3, 3)` is immediately overwritten with `np.zeros((6, 1))` (`:1262–1263`), so the expected scale `sqrt(np.pi * s2_star + f_s2)` reduces to `sqrt(f_s2)` and the `np.pi` factor — which is wrong for this noise object anyway; the correct factor is 1, the feature being unscaled `user_provided_add` — is never exercised. Un-zeroing `s2_star` to 0.7 makes the test's own formula differ from the returned `lpd` by 5.9 nats while the plain `s2_star + f_s2` matches to 7e-15 (`e11_misc.py`). As it stands the test pins only the case where the total noise is `np.spacing(1)`, and it would not catch an error in the noise contribution to the lpd — the very thing the first question asks about. `test_empty_gp` and `test_random_function` check `lpd` shapes only.
- **The quadrature tests mirror a freshly computed posterior.** `test_quadrature_with_noise_matches_numerical_integration` and `test_quadrature_with_noise_fitting` are the strongest tests in my slice — an independent Gauss–Hermite reference over `predict_full`, three noise parameterizations, per-sample and averaged, `rtol=1e-9` — and they are why I could confirm `quad`'s formulas so quickly. But every call is made on a posterior that `__core_computation` has just produced, where `min(sn2)·sn2_mult` and `Posterior.sl` coincide by construction; the distinction `Posterior.sl` exists for is never exercised, so F2 is invisible to them. One call to `quad(compute_var=True)` after `update(X_new=<one point>, s2_new=<smaller than the rest>)` would close the gap.
- **No test reads the plausible bounds or the starting points of any component.** `test_setting_bounds` (`:917`) and its isotropic counterpart compare `get_recommended_bounds` with `covariance.get_bounds_info(...)["LB"]`/`["UB"]` — that is, they assert that the assembler passes the components' own values through, which is a mirror of the implementation and holds whatever those values are. `PLB`, `PUB` and `x0` appear in no assertion in the suite, which leaves F4, F5 and F6 entirely uncovered; the four component test modules test `compute` and its gradients only.
- **`predict_full`'s noise path is tested only where it degenerates.** `test_empty_gp:73` calls `predict_full(x_star, add_noise=True)` on a GP with constant noise, where `sn2_star` is a scalar and `np.dot(np.eye(N), sn2_star)` is the correct `sn2·I`; the vector case that F1 breaks has no test. `gauss_hermite_quadrature_reference` always passes `add_noise=False`.
- **`__robust_cholesky`'s fallback is untested.** Both `random_function` tests draw at generic points; nothing constructs a singular predictive covariance, and nothing asserts that the draws' empirical covariance matches `predict_full`'s (`e4`/`e6` show that such an assertion separates the working path from the broken one cleanly).
- **What the suite does cover well, for the record:** `test_predict_cross_covariance.py` is a careful specification test of the 1.2.0 API (shapes, one entry per sample independently of `separate_samples`, `None` for prior-only GPs, no dependence on `add_noise`/`s2_star`, the copy path for overridden `compute`); `test_solve_triangular_matches_scipy` is parameterized over memory order and `trans`; `test_predict_mean_fallback_without_batched_method`, `test_predict_preserves_overridden_mean_compute` and `test_predict_custom_batched_mean_inheritance` pin the batched-mean gating in `predict` against `predict_full`'s per-sample loop; `test_compute_batched_matches_compute` covers all three means.
