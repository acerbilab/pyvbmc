### Question 2 — is the rank-one extension in `update` equal to a full recomputation?

**Yes in every state a default PyVBMC run can reach, and in every state I could construct with a noise floor, to 3e-15 in `alpha` and 1e-14 in the predictions.** The algebra is right: I re-derived both branches against `gplite_post.m:226–244` and gpyreg generalizes them correctly. With `u = L^{-T} k_*` and the stored scale `sl`, the new column `u/sl` and the new diagonal `sqrt(sl·sn2_eff + sl·k_{**} - u^T u)/sl` satisfy `L_new^T L_new = (K_aug + sn2_mult·diag(sn2_aug))/sl`; MATLAB's `sqrt(1 + K/sn2_eff - c^T c)` is the same expression specialized to `sl == sn2_eff`, which is what homoskedastic noise makes it. The low-noise branch is MATLAB's block inverse verbatim, and the `alpha` update `[alpha;0] + (m_*-y_*)/v_* · [u;-1]` is the exact block-inverse result provided `v_*` is the Schur complement including noise — which it is, `predict(..., add_noise=True)` returning `s2 + sn2_star*sn2_mult` as `gplite_pred.m:121` does.

### F1. The slice sampler's burn-in summary window differs from `slicesamplebnd.m` when the burn-in is odd, changing the adapted widths and the hyperparameter samples
- Location: `gpyreg/slice_sample.py:562` (and `:568`); MATLAB: `gplite/private/slicesamplebnd.m:362` (and `:368`)
- Category: control flow
- Proposed classification: port discrepancy (the defect is on the MATLAB side; gpyreg is the self-consistent one)
- Confidence: high
- History: the line is unchanged in MATLAB since before the port began; `fcf2674` touched only the bracket clipping.
- What the code does. MATLAB accumulates the running sums over `ii <= burn && ii > burn/2`, then at `ii == burn` divides by `burnstored = floor(burn/2)`. gpyreg accumulates over `burn/2 <= i < burn` (0-based `i = ii - 1`) and divides by the same `floor(burn/2)`. For even `burn` the two index sets coincide exactly. For odd `burn` they do not: MATLAB's set is `{floor(burn/2), …, burn-1}` in 0-based terms, `ceil(burn/2)` iterations, while gpyreg's is `{ceil(burn/2), …, burn-1}`, `floor(burn/2)` iterations. MATLAB therefore sums `ceil(burn/2)` terms and divides by `floor(burn/2)`, so its `xx_sqsum/burnstored - (xx_sum/burnstored)^2` is not a variance at all: it is `(k+1)/k·E[x²] - ((k+1)/k)²·E[x]²`, which is negative whenever the coordinate's coefficient of variation is small. MATLAB then takes `sqrt` of a negative number, gets a complex vector, and `if ~isreal(newwidths); newwidths = widths; end` (`:371`) discards the estimate for **every** coordinate, keeping the shrink-adapted widths instead. gpyreg's estimate is a genuine variance (its `np.maximum(..., 0)` at `:574` never triggers for that reason).
- Consequence if real. The widths the sampler uses after burn-in differ, so the hyperparameter samples differ. **Reached by a default PyVBMC run**, in a large fraction of its iterations: `_get_gp_training_options` sets `burn = thin*3 = 15` (always odd at `gp_sample_thin = 5`) in the branch that does not recompute the variational posterior, and `burn = thin*gp_s_N` otherwise, which is odd whenever `gp_s_N` is odd — `gp_s_N = round(80/sqrt(N))` passes through 7, 5, 3 as the run grows. `get_GPTrainOptions.m:108` sets the same `Thin*3`. On a realistic 34-point 2-D GP posterior at PyVBMC's defaults (`thin=5, n_samples=10, burn=15`, `burn_on_real_gp.py`) the adapted widths differed by up to a factor of 19 (`log sn`: 0.83 against 15.80; `log ell_1`: 0.234 against 0.958), the ten thinned hyperparameter samples by up to 2.13 in a coordinate, and their per-coordinate means by up to 0.29 nats (`m0`). Size: this is the largest effect I found, and it propagates into everything downstream of the hyperparameter samples.
- Suggested reproduction, and its result. `slice_burn_window.py` runs gpyreg's `SliceSampler` and a line-for-line transcription of `slicesamplebnd.m` on the same target from the same seeded generator. For `burn = 50` and `burn = 8` the samples and the final widths are **bit-identical** (max difference 0.000e+00), which also validates every other line of the sampler — the bracket resets, the draw order, the shrink-loop width adaptation, `LB_out`/`UB_out`, and the record/thin bookkeeping. For `burn = 15` and `burn = 9` the widths differ by up to 1.83 and the samples by up to 7.35.
- Test adequacy: no. `test_slice_sample.py` has 24 tests; none compares the adapted widths or the sampled chain against a reference implementation, and none exercises an odd burn-in. The distributional tests (`test_normal`, `test_multivariate_normal`, …) pass under either window.

### F2. `__robust_cholesky` transcribes the eigenvector sign normalization as an element mask instead of a column flip, so `T^T T` is not the input matrix
- Location: `gpyreg/gaussian_process.py:2620–2622`; MATLAB: `gplite/gplite_rnd.m:97–99`
- Category: indexing/shape
- Proposed classification: port discrepancy
- Confidence: high
- History: `gplite_rnd.m` has not changed since the port began.
- What the code does. MATLAB takes, for each **column** `j`, the row index `maxidx(j)` of that column's largest-magnitude entry, tests the entry `U(maxidx(j), j)`, and flips the sign of the whole column when it is negative — a sign convention that leaves `U(:,t)*diag(D)*U(:,t)'` unchanged. Python computes the same `maxidx` (`:2620`) but then writes `negidx = U[maxidx] < 0`, which is *row* fancy indexing: `U[maxidx]` is the `(m, m)` array whose row `i` is row `maxidx[i]` of `U`, so `negidx` is an element mask, and `U[negidx] *= -1` (`:2622`) flips individual entries of `U`. That destroys the orthogonality of the eigenvector matrix, so the returned `T = diag(sqrt(D)) @ U[:, t].T` no longer satisfies `T^T T = Sigma`.
- Consequence if real. `random_function` draws `f_* = T^T z + f_mu`, so whenever the plain Cholesky of the predictive covariance fails and the eigen branch is taken, the draw has the wrong covariance. Two further differences in the same function: `sp.linalg.eig` is used where MATLAB uses `eig` on a symmetrized matrix (`eigh` is the counterpart; `eig` returns complex eigenvalues and is less accurate for symmetric input), and the `p > 0` fall-back returns `np.zeros(sigma.shape)` (`:2635`), so a draw silently becomes the posterior mean with zero variance, where MATLAB returns an empty matrix and the caller errors. **Not reached by a default PyVBMC run:** `__robust_cholesky` is called only from `random_function` (`:2593`), which PyVBMC never calls.
- Suggested reproduction, and its result. `robustchol2.py` compares `GP.__robust_cholesky` with a transcription of `robustchol` on three matrices that make the plain Cholesky fail. Rank-deficient `B @ B.T`: gpyreg `max|T'T - C| = 6.71`, MATLAB `1.55e-15`. A squared-exponential kernel on duplicated test points: gpyreg `0.61`, MATLAB `6.66e-16`. One negative eigenvalue: gpyreg returns an all-zero `(5,5)`, MATLAB the empty matrix.
- Test adequacy: no. `test_random_function` (`test_gaussian_process.py:91`) only asserts the shapes of `predict(..., return_lpd=True)`; it makes no statement about the drawn function's covariance and never forces the eigen branch.

### F3. The hyperprior type masks mis-parse `df == 0 | ~np.isfinite(df)`, so a non-finite `df` gets no prior where MATLAB gives a Gaussian — and the normalization constants disagree with the masks on the same input
- Location: `gpyreg/gaussian_process.py:1441` and `:1457`; MATLAB: `gplite/gplite_hypprior.m:36`
- Category: formula
- Proposed classification: port discrepancy
- Confidence: high
- History: `gplite_hypprior.m` has not changed since the port began.
- What the code does. In Python, `|` binds tighter than `==`, so `df == 0 | ~np.isfinite(df)` parses as `df == (0 | ~np.isfinite(df))`, that is `df == 0.0` where `df` is finite and `df == 1.0` (always False) where it is not. MATLAB's `(df == 0 | ~isfinite(df))` in `gidx` is the intended `(df == 0) | ~isfinite(df)`, and `gplite_nlZ.m`'s header documents the convention: "Set HPRIOR.nu(i) = Inf to have instead a Gaussian prior for the i-th hyperparameter". With `df = inf` and finite `mu`, `sigma`, gpyreg's `u_idx`, `sb_idx`, `sb_t_idx`, `g_idx` and `t_idx` are **all False**, so that hyperparameter gets no prior contribution at all. The same file is internally inconsistent: `__recompute_normalization_constants` (`:1398`, `:1405`) writes the same test correctly as `if df == 0 or not np.isfinite(df)`, so it computes a *Gaussian* truncation constant for a hyperparameter the masks give no prior.
- Consequence if real. A Gaussian hyperprior requested with `df = inf` is silently dropped, and the log posterior is offset by the stray normalization constant of a prior that is not there. **Not reached by a default PyVBMC run:** `set_priors` encodes a Gaussian as `df = 0` (`:556`), which the mis-parsed expression still handles, and `fit` (`:1150`) fills every NaN `df` with `df_base = 7`; `_gp_hyp` sets only `student_t` priors with `df = 3`. Reaching it takes a `df` of `inf` written into `gp.hyper_priors["df"]` directly. Note that the comments at `:555`, `:566`, `:571` ("Implicit flag for gaussian, is set to inf later") describe a conversion to `inf` that never happens.
- Suggested reproduction, and its result. `priors_and_chol.py` §1–§3. `df = [0, 3, 7, inf, nan]` gives `as written [True False False False False]` against `as intended [True False False True True]`. A GP whose `covariance_log_lengthscale` prior is `("student_t", (0.0, 1.0, inf))` returns `log_posterior − log_likelihood = +5.7e-7`, exactly the stray `−log_norm`, instead of a Gaussian log density.
- Test adequacy: no. `test_prior_mask_cache_follows_priors_and_bounds` (`:1676`) compares a cached GP with an uncached GP — it mirrors the implementation, not the specification — and only uses `df` values of 0, 3 and NaN.

### F4. The uniform-prior test uses `and` where `gplite_hypprior.m` and `fminfill.m` use `||`, so MATLAB's documented flat prior (`sigma = Inf`) makes gpyreg's log posterior NaN
- Location: `gpyreg/gaussian_process.py:1453`; `gpyreg/f_min_fill.py:119`; MATLAB: `gplite/gplite_hypprior.m:35`, `gplite/private/fminfill.m:73`
- Category: control flow
- Proposed classification: possibly intentional (the `and` is what the Python-only smooth-box families need) with an unhandled remainder
- Confidence: high on the behavior, medium on the classification
- History: neither MATLAB line has changed since the port began.
- What the code does. MATLAB's `uidx = ~isfinite(mu) | ~isfinite(sigma)` marks a hyperparameter as having no prior if *either* the location or the scale is not finite; `gplite_nlZ.m`'s header documents the second half: "Set HPRIOR.sigma(i) = Inf to have a (non-normalized) flat prior over the i-th hyperparameter". gpyreg's `u_idx = ~isfinite(mu) & ~isfinite(sigma)` requires *both*. The `and` is necessary for gpyreg's smooth-box families, which are identified by a non-finite `mu` with a finite `sigma`, so the change itself is deliberate; what is missing is a replacement for the two cases MATLAB's `||` used to absorb. With a finite `mu` and `sigma = inf`, `t_idx` becomes True and the Student's-t term contributes `-log(inf) = -inf`; the truncation constant `cdf_ub - cdf_lb` is then 0, `log_norm = -inf`, and `lp` comes out NaN. With `mu` non-finite, `sigma` finite and no `a`/`b`, `t_idx` is True again and `z2` is NaN, so `lp` is NaN. The same `and` in `f_min_fill.py:119` sends a finite-`mu`, non-finite-`sigma` hyperparameter into the Student's-t branch, where `t.cdf((LB-mu)/nan)` fills that whole design column with NaN.
- Consequence if real. A flat prior expressed MATLAB's way turns the whole GP log posterior into NaN, which the slice sampler reports as "Target density function returned NaN" and treats as `-inf` at every point, so the chain cannot move. **Not reached by a default PyVBMC run:** every prior `_gp_hyp` installs has a finite `mu` and a finite `sigma` (`noise_std ∈ {0.5, log 10}`, `noise_mult_std ∈ {log(10)/2, log 10}`, `gp_length_prior_std = 0.5*log(1e3)`), and hyperparameters with no prior have `mu` and `sigma` both NaN, which the `and` handles correctly.
- Suggested reproduction, and its result. `priors_and_chol.py` §2–§3: for `("student_t", (0.0, inf, 3))`, `log_posterior` is `nan` while `log_likelihood` is `-5.406`; the mask table prints `python {u: False, t: True}` against `MATLAB {uniform: True}`. For `mu = nan, sigma = 1, df = 3` the same disagreement.
- Test adequacy: no. No test in `test_gaussian_process.py` or `test_smoothbox*.py` passes a non-finite `sigma` or a non-finite `mu` without `a`/`b`.

### F5. `fit`'s low-noise starting point is written through a view into the space-filling design, and `widths_default` is then computed from the modified design — after the substitution, where `gplite_train.m` computes it before and from a copy
- Location: `gpyreg/gaussian_process.py:1243`, `:1259`, `:1262`; MATLAB: `gplite/gplite_train.m:206–207`, `:220`
- Category: state/caching
- Proposed classification: port discrepancy
- Confidence: high
- History: the MATLAB lines have not changed since the port began.
- What the code does. `hyp = X0[0 : np.maximum(opts_N, 1), :]` (`:1243`) is basic slicing, hence a **view** of the design returned by `f_min_fill`. The low-noise extraction then writes `hyp[1, :] = xx[idx_best, :]` (`:1259`), which mutates `X0[1, :]`. Three lines later `widths_default = np.std(X0, axis=0, ddof=1)` (`:1262`) is computed from the mutated design. MATLAB copies at `:206` (`hyp(:,:) = output_fill.X(1:Nopts,:)'`), computes `widths_default = std(output_fill.X,[],1)` at `:207` — *before* the low-noise block at `:210–221` — and `hyp(:,2) = xx(idx_best,:)'` at `:220` writes into `hyp`, never into `output_fill.X`. Two deviations (aliasing and order) compound into one effect: gpyreg's default sampler widths reflect the substituted row, MATLAB's do not.
- Consequence if real. The default widths handed to the slice sampler differ, so the hyperparameter samples differ. Requires `noise_N > 0 and 1 < opts_N < init_N` (`:1246`), which **gpyreg's own default options satisfy** (`opts_N = 3`, `init_N = 1024`, `n_samples = 10`), so a plain `GP.fit()` is affected. **Not reached by a default PyVBMC run:** `_get_gp_training_options` yields `opts_N = 2` only in the branch where `gp_s_N == 0`, and with `n_samples = 0` `fit` returns at `:1327` before the widths are used; all other PyVBMC branches give `opts_N ∈ {0, 1}`.
- Suggested reproduction, and its result. `fit_details.py` replays `fit`'s lines against a copy of the design. `hyp.base is X0` is True; `X0[1]` changes; the widths differ by up to 4.98e-2 relative at `init_N = 128` (the noise coordinate: 2.4393 against 2.5609), 1.78e-2 at 64 and 1.65e-1 at 8.
- Test adequacy: no. `test_fitting`, `test_fitting_options` and `test_fit_seed_continues_design_stream` check only that a fit runs, that options are honored, and that a seeded fit is reproducible; none inspects `widths_default` or the design after the call.

### F6. The scalar-`sn2` noise-gradient loop indexes `dsn2` along the wrong axis: gpyreg raises where MATLAB silently reads the wrong entry
- Location: `gpyreg/gaussian_process.py:2813–2820`; MATLAB: `gplite/private/gplite_core.m:252–253`
- Category: indexing/shape
- Proposed classification: suspected defect in both
- Confidence: high
- History: the MATLAB lines have not changed since the port began.
- What the code does. In the `isscalar(sn2)` branch, `dsn2` may still be an `(N, noise_N)` array, because its shape is decided by `any(noisefun(2:end)>0)` while the branch is decided by `isscalar(sn2)`, and the two can disagree: `noisefun = [1 2 0]` with an empty `s2` gives a scalar `sn2` and an `(N, 2)` gradient. MATLAB writes `dnlZ(Ncov+i) = 0.5*sn2_mult*dsn2(i)*trQ`, and linear indexing on a column-major `(N, Nnoise)` array makes `dsn2(2)` the element `(2,1)` — the *second training point's* derivative with respect to the *first* hyperparameter — where `(1,2)` is wanted. gpyreg writes `np.dot(dsn2[i], tr_Q)` and `dsn2[i]` is *row* `i`, then `.item()` on the resulting length-`noise_N` array raises `ValueError`. Both are wrong; the correct element is `dsn2[0, i]`. (MATLAB happens to be right for `Nnoise == 1`, and so is gpyreg, since row 0 then has one element.)
- Consequence if real. `log_likelihood(..., compute_grad=True)`, `log_posterior(..., compute_grad=True)` and the optimizer phase of `fit` raise for a GP whose noise function declares more than one hyperparameter while the total noise is constant, and MATLAB returns a wrong gradient for the same configuration. **Not reached by a default PyVBMC run:** `scale_user_provided=True` is used only at `uncertainty_handling_level == 1` (`vbmc.py:1181`), where `FunctionLogger.noise_flag` is True by construction (`function_logger.py:199`), so `_get_training_data` always supplies `s2_train` and `sn2` is a vector. The `rectified_linear_output_dependent_add` case needs `y is None`, in which no gradient is taken.
- Suggested reproduction, and its result. `noise_grad.py`. `constant + scaled s2 (s2 omitted)` → `ValueError: can only convert an array of size 1 to a Python scalar`. Every configuration in which `sn2` is a vector, and the `noise_N == 1` scalar cases, match finite differences to 1e-9 or better.
- Test adequacy: no. `test_gp_gradient_computations` and `test_log_likelihood_and_posterior_gradients` always pass `s2` when the noise function scales it, so the mismatched-shape branch is never entered.

### F7. Neither the space-filling design nor the optimizer loop catches an exception from the objective, where `fminfill.m` and `gplite_train.m` both do
- Location: `gpyreg/f_min_fill.py:184–185`; `gpyreg/gaussian_process.py:1305–1320`; MATLAB: `gplite/private/fminfill.m:104–110`, `gplite/gplite_train.m:276–296`, and `gp_objfun`'s `try`/`catch` at `:516–546`
- Category: control flow
- Proposed classification: port discrepancy
- Confidence: high on the code, low on the reach
- History: the MATLAB lines have not changed since the port began.
- What the code does. MATLAB's design loop wraps each evaluation (`try ... catch % Something went wrong, try to continue`), so a failing start keeps its preset `Inf` and sorts to the end; its optimization loop wraps each `fmincon` call (`catch % Could not optimize, keep starting point`) and leaves `nll(iTrain) = Inf`; and `gp_objfun` itself catches everything and returns `NaN`, `NaN(size(hyp))`. gpyreg has none of the three: `y[i] = f(X[i, :])` and `sp.optimize.minimize(...)` propagate, so one failing hyperparameter vector aborts the whole `fit`. A *value* of NaN is handled equivalently on both sides — `np.argsort` and MATLAB's `sort` both put NaN last, and the sampler's `__log_pdf_bound` maps a NaN target to `-inf` as `logpdfbound` does — so only raised exceptions differ.
- Consequence if real. A `LinAlgError` from `__core_computation`'s retry ladder, or any other exception at one design point, ends the GP fit and the PyVBMC run instead of costing one starting point. The trigger is remote in a default run: with `min(sn2) >= 1e-5` the `L_chol` branch factorizes `K/sl + diag(sn2/sn2_div)`, whose diagonal is at least 1, so ten successive failures are not realistic — which is also why I could not produce `sn2_mult > 1` without removing the noise floor. Reachable in principle through a custom kernel, a user-supplied `s2` with extreme values, or a target whose `y` makes the mean-function bounds degenerate.
- Suggested reproduction, and its result. `fit_details.py` §2 passes `f_min_fill` an objective that raises on its fifth call: `f_min_fill propagated LinAlgError`, where `fminfill.m` would leave `y(5) = Inf` and carry on.
- Test adequacy: no test passes a raising objective to `f_min_fill` or to `fit`.

### Minor observations

- **M1. `hyp_start` is not re-clamped into the bounds and fixed dimensions are not pinned.** `gplite_train.m:304–306` does `hyp_start = min(max(hyp_start',LB+eps(LB)),UB-eps(UB))'` and then `hyp_start(LB == UB) = LB(LB == UB)`; `fit` (`:1322–1326`) takes SciPy's `res.x` as it is. SciPy keeps `x` inside the box and returns exactly `c` for a `(c, c)` bound, so the outcome agrees except that MATLAB nudges a bound-hugging start one `eps` inside. Related: `fit`'s `eps_LB`/`eps_UB` clamp (`:1296–1303`) nudges only finite bounds with `LB != UB`, where MATLAB relies on `eps(Inf) = NaN` and `min`/`max` ignoring NaN to get the same effect for infinite bounds, and sets `hyp = c - eps(c)` for `LB == UB == c` where Python sets exactly `c`.
- **M2. `hyp_dict["logp"]` is fed the wrong field of the sampling result.** `gaussian_process_train.py:178` assigns `res["log_priors"]`, which `SliceSampler.__log_pdf_bound` fills with `0` for every sample when no `log_prior` callable is given — so it is an array of zeros. `gptrain_vbmc.m:66` stores `gpoutput.logp`, the *thinned* log posterior of the samples (`gplite_train.m:461`); `res["f_vals"]` is its counterpart. The only MATLAB reader is commented out (`gptrain_vbmc.m:32`) and PyVBMC has none, so nothing depends on it; gpyreg's field name invites the confusion. MATLAB also stores the thinned values where PyVBMC stores an array of pre-thinned length.
- **M3. The rank-one stability guard is Python-only and does not cover the low-noise branch.** `:872–887` reverts to a full recomputation when the new Cholesky diagonal's radicand is non-positive; `gplite_post.m` has no such guard. PyVBMC calls `gp.get_priors()` (`gaussian_process_train.py:421`) but only ever sets `student_t` priors, whose `a`/`b` are NaN, so the short circuit keeps the line unreached.

## 4. Test adequacy notes

Tests that mirror the implementation rather than the specification, in my judgment:

- **`test_prior_mask_cache_follows_priors_and_bounds` (`test_gaussian_process.py:1676`)** compares a GP that cached its masks against a GP that did not, and `log_posterior` against `log_posterior` of the same code. It can only detect a stale cache, never a wrong mask — which is why F3 and F4 are invisible to it. A specification test would compare `__compute_log_priors` against an independent evaluation of the Gaussian and Student's-t log densities for each documented `(mu, sigma, df, a, b)` combination, including the non-finite ones `gplite_nlZ.m`'s header names.
- **`test_random_function` (`:91`)** asserts only the shapes of the `return_lpd` outputs. It calls `random_function` three times and never checks the drawn function against the covariance it should have, so F2 survives it. It also never reaches the eigen branch of `__robust_cholesky`, which has no test of its own.
- **`test_slice_sample.py`'s distributional tests** (`test_normal`, `test_normal_mixture`, `test_exponential`, `test_uniform`, `test_beta`, `test_multivariate_normal`, `test_multivariate_t`) check sample means and variances against the target's, which passes under any sensible width adaptation and under F1's window either way. The one test that pins a mechanism, `test_evaluations_stay_on_coordinate_line` (`:49`), was written for the fix in `f610e11` and does the right thing: it inspects where the target was evaluated. Nothing comparable exists for the burn-in width update, and no test uses an odd burn-in.
- **`test_healthy_chain_effective_n_matches_reference` (`:218`)** is the right shape of test (an external reference) but it pins gpyreg's Geyer/ArviZ-style `__effective_n`, which is a substitution for MATLAB's external `psrf` (absent from the VBMC repository, so MATLAB's own diagnostics would error and return NaN). The diagnostics are off in `gplite_train` and in `fit`, so this is a gpyreg-only surface.
- **The rank-one update tests are good**, and unusually so: `test_rank_one_update_with_heteroskedastic_noise` compares `L.T @ L * sl` rather than `L`, which correctly accommodates the deliberate scale difference, and its three cases cover `s2_new` given, `s2_new` omitted and output-dependent noise. What they do not reach: the `L_chol == False` branch (all three assert `post.L_chol and post_ref.L_chol`), more than one hyperparameter sample, a stored `sn2_mult > 1`, and a new point whose noise crosses the `1e-6` threshold. Those are the states Question 2 asks about, and I covered them in `q2_rank_one.py` and `q2b_sn2mult.py`.
- **`test_gp_gradient_computations` (`:310`) and `test_log_likelihood_and_posterior_gradients` (`:1662`)** are finite-difference tests, the right instrument, but they only ever pass `s2` when the noise function scales it, so the shape-mismatched branch behind F6 is never entered.
